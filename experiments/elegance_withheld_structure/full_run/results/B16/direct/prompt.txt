Public API and data-format contract (frozen):

`proposal` has keys `beds` (mapping bed id to `{"neighbors": [bed ids], "accessible": bool}`), `crops` (mapping crop id to `{"family": str, "plant": [date,date], "harvest": [date,date], "incompatible_families": [str], "required_predecessor": str or None}`), `assignments` (list of `{"id": str, "bed": str, "crop": str, "plant": date, "harvest": date, "volunteer": str, "locked": bool}`), `volunteers` (mapping volunteer id to `{"needs_accessible": bool}`), and `previous_crops` (mapping bed id to a list of crop ids, most recent last). `observations` is a list of `{"kind": "bed_unavailable", "bed": str, "start": date, "end": date}`. `next_season_start` is a date.

The result is a dictionary with exactly these top-level keys: `issues`, `work_cards`, `volunteer_views`, `bed_calendar`, `next_season`. Issues are dictionaries `{"code": str, "assignments": [assignment ids], "bed": str}`. Required codes are `OCCUPANCY_OVERLAP`, `NEIGHBOR_CONFLICT`, `PREDECESSOR_MISSING`, `INACCESSIBLE_ASSIGNMENT`, `BED_UNAVAILABLE`, `OUTSIDE_PLANTING_WINDOW`, and `OUTSIDE_HARVEST_WINDOW`; every applicable issue is returned, sorted by `(code, bed, assignments)`. Within every issue, assignment ids are sorted. For a two-bed neighbor issue, `bed` is the lexicographically smaller bed id; otherwise it is the affected bed. Date intervals are inclusive. An assignment outside its crop's inclusive harvest window produces `OUTSIDE_HARVEST_WINDOW`. A neighbor conflict exists when assignments in neighboring beds have overlapping inclusive plant-through-harvest intervals and either crop lists the other's family as incompatible. An overlap is two assignments in the same bed with intersecting intervals. A predecessor requirement is met only when the required crop id occurs in that bed's `previous_crops`.

`work_cards` contains two cards per assignment, `{"date": date, "kind": "plant" or "harvest", "assignment": id, "bed": id, "volunteer": id}`, sorted by `(date, kind, assignment)`. `volunteer_views` maps every volunteer id to that volunteer's cards in the same order. `bed_calendar` maps every bed id to its assignments as `{"assignment": id, "crop": id, "start": date, "end": date}`, sorted by `(start,end,assignment)`. These views are produced even when issues exist.

`next_season` is a list with one entry per assignment, in assignment-id order. Each entry is `{"assignment": id, "bed": id, "crop": id, "plant": date, "harvest": date, "volunteer": id, "locked": bool, "automatic_changes": [str]}`. Locked entries preserve all explicit assignment values and have an empty change list. For an unlocked entry, shift both dates forward by the whole-year offset from the proposal's earliest planting year to `next_season_start.year` (using `date.replace`, and February 29 becomes February 28 if needed), preserving bed, crop, and volunteer; its change list is `['plant','harvest']` if either shifted date differs and otherwise empty. Mapping insertion order must not affect the result.
